# 5.5_응용 계층 - HTTP의 기초
## DNS와 URI/URL
### 도메인 네임과 DNS
네트워크 상의 호스트를 식별하기 위해 기본적으로 사용되는 정보: IP\
하지만 아래와 같은 문제가 있음
- 특정 호스트의 특징을 나타내기 어려움
- 호스트의 IP 주소는 언제든지 바뀔 수 있음
=> **도메인 네임** 등장

도메인 네임: 'www.example.com, developers.naver.com, git.kernel.org'와 같은 문자열 형태의 호스트 특정 정보로, 호스트의 IP 주소와 대응됨\
장점
- IP 주소에 비해 기억이 쉬움
- IP 주소만으로 호스트를 특정하는 것보다 간편함(IP 주소가 바뀌더라도 바뀐 IP 주소에 도메인 네임을 다시 대응하면 됨)

네임 서버(name server): 도메인 네임과 그에 대응하는 IP 주소를 관리하는 서버\
DNS 서버(DNS server): 도메인 네임을 관리하는 네임 서버

IP 주소를 모르는 상태에서 도메인 네임에 대응된 IP 주소를 알아내는 과정 === '도메인 네임을 풀이(resolve)한다' === '리졸빙(resolve+ing) 한다'

![alt text](image-111.png)

<도메인 네임의 계층적 구조>
- 하나의 도메인 네임은 점(.)을 기준으로 계층적으로 분류됨
- 최상단에 **루트 도메인**이 있고, 다음 단계에는 **최상위 도메인(TLD_Top-Level-Domain)**이 있음
- > 대표적인 최상위 도메인: 'com, net, org, kr(대한민국), jp(일본), cn(중국), us(미국)'
- > ex) 'www.example.com'의 최상위 도메인: 'com'
  - 2단계 도메인(세컨드 레벨 도메인_second-level-domain): 최상위 도메인의 하부 도메인
  - 3단계 도메인: 2단계 도메인의 하부 도메인
- 일반적으로 3~5단계 정도로 구성됨
- 전체 주소 도메인 네임(FQDN_Fully-Qualified Domain Name): 'www.example.com'처럼 도메인 네임을 모두 포함하는 도메인
  - FQDN을 알면 호스트를 식별할 수 있음
- ![alt text](image-112.png)

<네임 서버의 계층적 구조>
- 네임 서버는 분산되어 관리됨
- **도메인 네임 시스템(DNS_Domain Name System)**: 계층적으로 분산되어 있는 도메인 네임에 대한 관리 체계
  - DNS는 호스트가 이러한 DNS를 이용할 수 있도록 하는 애플리케이션 계층 프로토콜을 의미하기도 함
- ex) 'minchul.net'이라는 도메인 네인을 통해 IP 주소를 알아내고자 하는 경우
- 호스트는 가장 먼저 로컬 네임 서버에게 도메인 네임을 질의하게 됨
  - 로컬 네임 서버: 
    - 클라이언트와 맞닿아 있는 네임서버
    - 클라이언트가 도메인 네임을 통해 IP 주소를 알아내고자 할 때 가장 먼저 찾게 되는 네임 서버
    - ISP가 로컬 네임 서버의 주소를 자동으로 할당해줌
- 로컬 네임 서버 주소 또는 **공개 DNS 서버**를 이용해 로컬 네임 서버에 접근
  - ex) 공개 DNS 서버의 대표적 예: 구글 '8.8.8.8, 8.8.4.4', 클라우드플레어 '1.1.1.1'
  - ![alt text](image-113.png)
- 로컬 네임 서버가 FQDN에 대응하는 IP 주소를 
  - 알고있을 경우 => 해당 IP 주소를 반환
  - 모르고 있을 경우 => 로컬 네임 서버는 FQDN에 대응하는 IP 주소를 알아낼 때까지 루트 네임 서버, TLD 네임 서버, 하위 레벨의 도메인 네임을 관장하는 네임 서버, ... 등에 거쳐 질의하여 클라이언트에게 반환할 IP주소를 알아냄
    - 루트 네임 서버: 도메인 네임의 루트 도메인을 관장하는 서버
    - TLD 네임 서버: 최상위 도메인을 관장하는 서버
  - ![alt text](image-114.png)
- 하지만 IP를 알아내는 과정에서 질의 과정이 너무 많이 반복되면 네트워크 내 트래픽이 많아짐 -> DNS 캐시를 이용해 해결
  - DNS 캐시: 네임 서버들이 기존에 응답받은 결과를 임시로 저장하는 캐시
  - > DNS 서버에 캐시된 값은 저마다 TTL(Time To Live_캐시될 수 있는 시간)값이 정해져 있음 <- IP 해더 내의 TTL 필드와 무관한 내용

### 자원과 URI/URL
- 자원: 프로그램 실행에 마땅히 필요한 요소
  - 네트워크에서의 자원: 네트워크 상의 메시지를 통해 주고받는 최종 대상
  - ex) HTML 파일, 이미지 동영상 파일, 텍스트 파일
- URI(Uniform Resource Identifier): 웹 상에서의 자원을 식별하기 위한 정보
  - 자원(Resource)을 식별(Indentifier)하는 통일된 방식(Uniform)
  - URN(Uniform Resource Name): '이름'을 기반으로 식별하는 방식
  - URL(Uniform Resource Locator): 위치로 자원을 식별하는 방식

**URL**\
URL의 구조
![alt text](image-118.png)
1. scheme
   - 자원에 접근하는 방법을 나타냄
   - 'http://'나 'https://'일 경우 각가 HTTP와 HTTPS를 사용하여 자원에 접근함을 나타냄

2. authority
   - 호스트를 특정할 수 있는 IP 주소나 도메인 네임이 명시됨
   - 콜론(:)뒤에 포트 번호를 명시할 수도 있음

3. path
   - 자원이 위치하고 있는 경로가 명시됨
   - 슬래시(/)를 기준으로 계층적으로 표현되며, 최상위 경로 또한 슬래시로 표현 됨
   - 'http 프로토콜로 접근 가능한 도메인 네임 example.com의 자원 중 /home/images/a.png에 위치한 자원'은 'http://example.com/home/image/a.png'로 표현할 수 있음

4. query
   - URL에 대한 매개변수 역할을 하는 문자열
   - 쿼리 문자열(query string), 쿼리 파라미터(query parameter)등으로도 불림
   - 'scheme, authority, path'만으로는 표현하기 어려운 추가정보
   - 물음표(?)로 시작되는 <키=값> 형태의 데이터
   - 앰퍼샌트(&)를 사용하여 여러 쿼리 문자열을 연결할 수 있음
   - ![alt text](image-119.png)

5. fragment
   - 자원의 일부분
   - 일반적으로 HTML파일과 같은 자원에서 특정 부분을 가리키는 데 사용됨
   - ![alt text](image-120.png)
   - (a)는 자원의 조각이 아닌 자원 그 자체(HTML 파일 자원 자체)를 가리키므로 HTML의 첫부분이 나타남
   - (b)는 HTML 자원의 특정 부분을 가리키므로 HTML 파일의 특정 부분으로 이동하여 보임

## HTTP의 특징과 메시지 구조
HTTP의 목적: 애플리케이션의 다양한 자원을 네트워크를 통해 송수신하는 것

### HTTP의 특징
1. 요청 응답 기반 프로토콜
   - 요청 메시지를 보내는 클라이언트와 이에 대한 응답 메시지를 보내는 서버가 서로 HTTP 요청 메시지와 HTTP 응답 메시지를 주고받는 구조로 작동함
   - 같은 HTTP 메시지라도 HTTP 요청 메시지와 HTTP 응답 메시지의 형태는 다름

2. 미디어 독립적 프로토콜
   - 다양한 종류의 자원을 주고받을 수 있음
   - HTTP는 주고받을 미디어 타입에 특별한 제한을 두지 않고, 독립적으로 작동이 가능한 **미디어 독립적인 프로토콜**이라 할 수 있음
   - 미디어 타입: HTTP에서 메시지로 주고받는 자원의 종류. 
     - 네트워크 세상의 확장자와 같음
     - '타입/서브타입'의 형식으로 구성됨
       - 타입: 데이터의 유형
       - 서브타입: 주어진 타입에 대한 세부 유형
       - ![alt text](image-122.png)
       - ![alt text](image-123.png)

> 미디어 타입의 추가 표기 방법\
> ![alt text](image-124.png)

3. 스테이트리스 프로토콜
   - 서버는 HTTP 요청을 보낸 클라이언트 관련 상태를 기억하지 않음
     - 일반적으로 HTTP 서버는 많은 클라이언트와 동시에 상호작용하기 때문에 상태정보를 유지하기에 부담이 됨
     - 여러 대로 구성된 서버가 모든 클라이언트 상태를 공유해야한다면 모든 서버가 클라이언트 상태 정보를 공유해야 함
     - ![alt text](image-125.png)
   - HTTP 서버가 지켜야 할 중요한 설계 목표: 확장성, 견고성

4. 지속 연결 프로토콜
   - 초기 HTTP 버전(HTTP 1.0이하)에서는 쓰리 웨이 핸드셰이크를 통해 TCP 연결을 수립한 후, 요청에 대한 응답을 받으면 연결을 종료하는 방식으로 동작함 => 추가적인 요청-응답 메시지를 주고 받으려면 매번 새롭게 연결을 수립하고 종료해야함(비지속 연결)
   - 최근 사용되는 HTTP 버전(HTTP 1.1 이상)에서는 지속 연결(persistent connection) 기술 제공
     - 킵 얼라이브(keep-alive)라고도 부름
     - TCP 연결 상에서 여러 개의 요청-응답을 주고받을 수 있는 기술
   - ![alt text](image-126.png)

2. POST

   - ex) 'http://info.cern.ch/hypertext/WWW/TheProject.html'에 GET 요청 메시지를 보낼 때의 HTTP 요청 메시지

     - 메시지 본문은 여러 번 압축/변환될 수 있으며, 이 경우 세 번째 예시와 같이 압축/변환된 순서대로 명시됨

# Q&A

Q1. HTTP의 특징에 대해 말해보시오.

A1. HTTP는 요청과 응답을 기반으로 동작하고, 미디어 독립적이며 상태를 유지하지 않고 지속 연결을 지원한다는 4가지 주요 특징이 있습니다.

Q2. HTTP 특징 중 하나인 지속 연결은 비지속 연결과 어떠한 차이가 있는지 간단히 설명하시오.

A2. 비지속 연결은 추가적인 요청-응답 메시지를 주고 받으려면 매번 새롭게 연결을 수립하고 종료해야하는 반면 지속 연결 방식은 TCP 연결 상에서 여러 개의 요청-응답을 주고받을 수 있는 차이가 있습니다.

Q3. HTTP 상태 코드 중 401과 403 상태 코드의 차이에 대해 설명하시오.

A3. 401은 인증을 요구하는 상태 코드, 403은 권한을 요구하는 상태 코드 입니다. 예를 들어 로그인된 모든 유저는 인증된 유저이지만, 로그인된 모든 유저가 관리자 페이지에 들어갈 수는 없듯 인증이 되었더라도 권한이 충분하지 않음을 구분하기 위해 사용됩니다.
